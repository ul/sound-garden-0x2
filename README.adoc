== What?
Sound Garden is a text based modular synthesis env. If you ever considered text like this
-----
.0625 .5 p 110 s * dup .5 t 0.0625 5 range 0.5 fb swap .125 t 0.0625 5 range 0.5 fb + .1 * 
-----
to be a valid musical notation and sound like https://soundcloud.com/ruslan-prokopchuk/rf-01[this]
to be a subject of interest then you might find Sound Garden worthwhile having a look at.

== (Inter)Faces of Sound Garden
Just a quick note before we start. Sound Garden is a set of libraries which fulfil various audio
synth and livecoding needs and binaries which provide multiple layers of experience, from just
producing sound when given a program to experiments with graphical tree-like representation. What
you've built and installed in the prev section is the "simplest" interface which just plays
programs and the "default" one which embodies Sound Garden aesthetics the most, but you are free to
interact with it your way.

=== First steps
Sound Garden is operated via simple concatenative stack-based language. The only type of element
to be put on stack is a frame. Frame is a pair of amplitude values, one for the left channel and
another for the right. Each sample (typically 44100 or 48000 times per second) Sound Garden
executes your program against empty stack and sends top frame values to audio driver.
Let's use the simplest Sound Garden interface to play tuning fork sound (please be sure to reduce
your speaker volume before running it!):
-----
$ echo '440 0 sine' | play_program
-----
`sine` word corresponds to the stack op which consumes frequency (440) and initial phase (0)
from the top of the stack and puts back the next frame of sine wave.
Many words in Sound Garden has aliases. Some aliases are just shorter forms which make quick
experiments easier for experienced users and some provide default val. For example `s` produces
the same sine wave but always starts with phase 0:
-----
$ echo '440 s' | play_program
-----
To compose Sound Garden programs just slap them together separated by whitespace. This is why it's
called concatenative:
-----
$ echo '440 s 0.5 *' | play_program
-----
`0.5 *` will reduce our sine wave amplitude by half. Each channel, every sample. 
Sound Garden is esoteric and sometimes cryptic but it's very forgiving. Unknown words or stack
overflows or underflow wouldn't explode but will be ignored.
As you are free to put any values on the stack to be consumed by following ops (stack operations in
Sound Garden lingo), you can easily make your sine wave more funky by modulating it with another
-----
$ echo '2 s 1 + 220 * s' | play_program
-----
Take some time to meditate on what happens here.
That's it about Sound Garden as a language (not really, it has few
more tricks in its sleeve to be revealed in <<Templates>> section!). Please find list of available ops
https://github.com/ul/sound-garden-0x2/tree/master/audio_program/src/help.adoc[here].
Now its time to dive into Sound Garden as a livecoding env.

=== Sound Garden GUI
`sound_garden_egui` is a GUI interface to Sound Garden which resembles a terminal modal editor.
At the moment you run it from the command line to provide it with the path to the tree and to configure other options.
-----
$ sound_garden_egui ~/Documents/my_tree.sg
-----

For lower latency, ask for a smaller audio buffer (clamped to what the device supports; the modeline shows what you got). Smaller buffers leave less headroom, so keep an eye on the DSP load:
-----
$ sound_garden_egui --buffer 128 ~/Documents/my_tree.sg
-----

To send programs to a separately running audio server instead of starting an embedded one, pass an audio control port. The engine status, meters, MIDI activity, compile warnings and oscilloscope capture described below come from the embedded server only.
-----
$ sound_garden_egui --audio-port 12345 ~/Documents/my_tree.sg
-----

The editor stores a tree as nodes on a two-dimensional grid. A node under the cursor can be edited as text, moved around, cycled through common operator variants, or committed to the audio engine. After editing, the modeline changes color to show that the workspace is draft; commit to make the current tree audible and mark it as known.

.Modeline
Left to right, after the transport:

* the value of the node under the cursor and its range over the last quarter second, e.g. `0.2500  -0.9800…0.9900`;
* help for the operator under the cursor — or, if the last commit warned about that node (an unknown word, a bad argument, an invalid pattern), the warning in red. Such nodes are also drawn in red and underlined until you edit them;
* the number of warnings in the last commit, if any;
* the connected MIDI input and the last message it sent, e.g. `midi: Keystation · cc 74 = 0.62`: turn a knob to see which `cc:N` to type;
* sample rate, buffer size and latency, and the peak DSP load (share of each buffer's time spent computing it); dropouts are counted and flash red when they happen;
* stereo level meters (RMS bar, held peak tick, warm above -6 dBFS) and a clip light that stays lit for a moment whenever the output goes past ±1 and is clipped.

.Oscilloscope
The oscilloscope panel shows the node under the cursor (or the program output). Periodic signals are drawn sample-accurately and triggered on a rising crossing so they stand still; slow signals such as LFOs and envelopes scroll as a trend instead. When the panel is wide enough, its right third shows the node's spectrum on a log-frequency axis with the Cs marked. Toggle it with `v`, resize it by dragging its top edge, and zoom with `Alt+=` / `Alt+-`.

=== Patterns
Patterns are signal-native cycle readers for direct musical development over time.
Use `cycle` (alias `cy`) to turn a cycles-per-second signal into wrapped `0..1` phase,
then read flat patterns with `pat`, `gate`, or `trig`:
-----
1 cycle pat:60,64,67,72 m2f s .2 *
-----
`pat:<PATTERN>` reads comma-separated numeric values. `gate:<PATTERN>` and
`trig:<PATTERN>` read dense visual rhythms where `x` is active and `.` is inactive;
`gate` stays high over active spans, while `trig` emits one-sample impulses when entering
active cells:
-----
220 s 1 cycle gate:x..x 0.01 0.1 0.0 0.2 adsr *
-----

-----
220 s 1 ctrig:x... 0.1 impulse *
-----
The `cpat`, `cgate`, and `ctrig` forms are CPS-consuming conveniences equivalent to
`cycle` followed by the corresponding phase-consuming reader.

=== Polyphony
A single pattern lane drives one voice: when a new note triggers, the previous note's tail is cut.
To let tails ring (or play overlapping gated notes), wrap the voice in a quotation and hand it to `poly:N`.
Square brackets collect compile-time quotations. `poly:N` consumes the preceding quotation as a voice body,
runs N copies of it, and sums their outputs:
-----
1 cycle pat:60,64,67,72 m2f 1 cycle trig:x.xx [ swap s swap 0.01 impulse * ] poly:4 .2 *
-----
`poly` consumes a value signal and a control signal. On a rising edge of the control signal it
allocates the next voice round-robin and latches the current value into it; each voice body then runs
every sample against a stack seeded with `(value, ctl)`. The most recently allocated voice receives
the live control signal as-is, other voices receive 0. This makes `poly` gate-transparent: a trig
body sees a one-sample impulse, while a gate body sees the full gate including its fall, so `adsr`
releases work naturally:
-----
1 cycle pat:60,64,67,72 m2f 1 cycle gate:x.xx [ swap s swap 0.01 0.1 0.7 0.3 adsr * ] poly:4 .2 *
-----
Control amplitude passes through unchanged, so gates can carry velocity. There is no note-off or
free-voice detection: if tails get stolen, raise N. Named templates work as voice bodies too:
`lead poly:4` pushes the registered `lead` quotation and lets `poly:4` consume it.

=== Compile-time quotations and templates
Square brackets collect a compile-time quotation. If the following word consumes it, that word decides
what to do with the quotation; otherwise the quotation auto-expands inline. For example:
-----
[ 440 s ] 0.2 *
-----
is equivalent to:
-----
440 s 0.2 *
-----

`def:<NAME>` registers the preceding quotation as a template; `:<NAME>` is equivalent sugar. Writing the
template name later pushes the registered quotation, which can auto-expand inline or be consumed by a
quotation-taking word such as `poly:N` or `drop`.

For example, the following
-----
[ dup s swap c * ] def:yay
440 yay 220 yay +
-----
will be expanded into
-----
440 dup s swap c * 220 dup s swap c * +
-----
Templates are livecoding-friendly, and replacing `s` in the template definition with `t`
would produce expanded `t`s with the same identity as corresponding `s`s before, preserving phase.

Dropped quotations are comments and may contain whitespace:
-----
[ bassline notes with spaces ] drop
-----
