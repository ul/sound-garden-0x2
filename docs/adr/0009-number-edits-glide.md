# Number edits glide; the reload declick corrects only what the signal can't explain

Changing a number in a running program (`0.2 *` to `0.1 *`) clicked even with the reload declick. An instant change to a running signal is a click whatever is done to the output afterwards: at a peak it is a jump in value, at a zero crossing a corner in slope that a value correction can't see. Measured on a 220 Hz sine, the old declick left the edit 42–53 dB below the tone depending on where in the cycle it landed; easing the number itself over 10 ms leaves it about 89 dB below, which is inaudible. So the ops that carry a literal (`Constant`, the folded `AddConst`/`MulConst`/`SubConst`/`DivConst` and reversed forms, `FixedOsc`) glide from the value their predecessor was producing to their own, with a raised cosine over 480 frames (10 ms at 48 kHz): too short to hear as a slide. Unchanged numbers stay bit-exact. A plain `Constant` rising from zero or below to positive switches at once instead, because a plain number may be a gate or trigger and the ops that latch amplitude on a rising edge (`adsr`, `impulse`, `poly`, `grain`) would otherwise latch the first tiny step of the glide; the folded ops always glide, as their output is a scaled or offset signal, not an edge.

Measuring this exposed a flaw in the declick: it compared the new program's first frame with the last frame heard, so a moving signal's own sample-to-sample change counted as a reload step, and every reload, even of an unchanged program, injected a small click (about −50 dB on a 220 Hz sine, −23 dB on 5 kHz) and smeared the wraps of saws and pulses. The declick now predicts the replaced frame by linear extrapolation from the last two and corrects the prediction error only when it exceeds twice the signal's own motion: the larger of its last two sample-to-sample changes and its curvature, all from the last three frames. No-op reloads and glided edits are now exact for sines up to 12 kHz, saws, pulses and impulse trains, while structural edits (squaring a signal, adding an offset) keep the full declick. A decaying peak of the motion over ~100 ms also worked and caught a reload landing exactly on a saw wrap, but tracking it every frame cost up to 13 ns per frame; judging motion only at reload time costs nothing while playing, and the price, one softened saw or pulse edge when a reload hits a wrap, is inaudible in practice. We kept the decaying-offset correction rather than a true crossfade because migration moves state from the old program to the new one, so the old program can't keep running to be faded out without cloning its state on the audio thread.

Ops that glide keep their common case a leaf function: they check whether a glide is running and, if so, return through a cold function called in tail position. Calling the glide step inline instead made every literal op set up a stack frame on every sample, which doubled the cost of the cheapest ops. Rendering the fourteen example pieces is 1.5% faster overall than before these changes (individual pieces within ±5%).
